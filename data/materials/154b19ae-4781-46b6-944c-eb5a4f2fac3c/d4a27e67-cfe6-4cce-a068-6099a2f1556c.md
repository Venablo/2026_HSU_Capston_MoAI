### 📌 이번 주차 전체 지도
지난 4주차에서 단순 CRUD를 위한 JPA Repository 기초를 다루었다면, 이번 7주차는 실제 실무 서비스에서 필수적인 '엔티티 간의 관계 매핑'과 '대용량 데이터 처리를 위한 페이징'을 학습합니다. 연관 관계의 주인 설정부터 시작하여, 프록시(Proxy) 기반의 지연 로딩을 통한 성능 최적화, 그리고 Spring Data JPA의 Pageable을 활용한 효율적인 데이터 탐색 순으로 학습을 진행합니다.

### 1️⃣ @ManyToOne (N:1 단방향/양방향)
- **정의**: 여러 개의 자식(N)이 하나의 부모(1)를 가지는 관계.
- **원리**: 외래 키(FK)를 가진 엔티티가 연관 관계의 주인이 됩니다. @JoinColumn을 사용하여 매핑합니다.
- **예시**: 게시물(Post)과 사용자(User) 관계. 여러 게시물은 한 명의 사용자에게 속합니다.
- **주의사항**: 양방향 시 mappedBy를 사용하며, 주인(N) 측에서만 값을 수정해야 합니다.
- **시험 포인트**: 연관 관계의 주인은 항상 FK가 있는 쪽입니다.

### 2️⃣ @OneToMany (1:N 양방향)
- **정의**: 하나의 부모(1)가 여러 자식(N)을 가지는 관계.
- **원리**: 1:N 단방향보다는 N:1 양방향을 지향합니다. mappedBy를 통해 읽기 전용으로 설정합니다.
- **예시**: 부서(Department)와 사원(Employee)의 관계.
- **주의사항**: 일대다 단방향은 쿼리가 복잡해지므로 실무에서 권장하지 않습니다.
- **시험 포인트**: @OneToMany에서 mappedBy가 없으면 별도의 조인 테이블이 생성되어 성능 저하를 유발합니다.

### 3️⃣ Lazy Loading (지연 로딩)
- **정의**: 연관된 엔티티를 실제 사용하는 시점에 로딩하는 기법.
- **원리**: 연관 객체를 프록시 객체로 채워두고, getter 호출 시점에 DB를 조회합니다.
- **예시**: @ManyToOne(fetch = FetchType.LAZY).
- **주의사항**: 트랜잭션 범위 밖에서 호출 시 LazyInitializationException 발생.
- **시험 포인트**: 즉시 로딩(EAGER)은 예측 불가능한 조인 쿼리를 생성하므로 무조건 지연 로딩을 사용하십시오.

### 4️⃣ Proxy (프록시)
- **정의**: 엔티티를 실제 DB에서 가져오지 않고 가짜 객체를 참조하는 기술.
- **원리**: 하이버네이트는 엔티티 상속을 통해 프록시를 생성합니다.
- **예시**: em.getReference()로 조회한 엔티티.
- **주의사항**: 프록시는 엔티티를 상속하므로 엔티티를 final로 선언하면 안 됩니다.
- **시험 포인트**: 프록시 객체는 실제 엔티티를 감싸고 있어 타입 체크 시 주의가 필요합니다.

### 5️⃣ Pageable & Pagination
- **정의**: 전체 데이터를 나누어 조회하는 방식.
- **원리**: Spring Data JPA의 Pageable 인터페이스를 사용하여 OFFSET/LIMIT 쿼리를 자동 생성합니다.
- **예시**: repository.findAll(PageRequest.of(0, 10)).
- **주의사항**: 전체 개수를 세는 count 쿼리가 추가로 실행되므로 대용량일 경우 Slice 사용을 고려합니다.
- **시험 포인트**: Page는 데이터와 함께 totalPage, totalElements 정보를 반환합니다.

### 6️⃣ 객체 그래프 탐색
- **정의**: 엔티티 간 연결된 관계를 타고 들어가 데이터를 조회하는 것.
- **원리**: 연관 매핑이 된 필드를 통해 자유롭게 참조합니다.
- **예시**: post.getUser().getName().
- **주의사항**: 불필요한 객체 탐색은 N+1 문제의 주범입니다.
- **시험 포인트**: 객체 그래프 탐색을 할 때는 반드시 영속성 컨텍스트 내에 있어야 합니다.

| :--- | :--- | :--- |

| 권장 여부 | X (실무 지양) | O (실무 권장) |

| :--- | :--- | :--- |

## 연습 퀴즈

1. JPA에서 연관 관계의 주인을 결정하는 가장 정확한 기준은 무엇인가?
   A. 비즈니스 로직상 더 중요한 엔티티
   B. 외래 키(FK)를 가지고 있는 테이블의 엔티티
   C. 데이터가 더 많이 저장되는 엔티티
   D. 먼저 생성된 엔티티
   정답: B
   관련 키워드: ManyToOne
   해설: JPA에서 연관 관계의 주인은 테이블 상 외래 키를 보유한 엔티티입니다. 외래 키의 위치에 따라 매핑의 방향성이 결정됩니다.

2. Lazy Loading(지연 로딩)을 사용할 때 주의해야 할 점은?
   A. 항상 조인 쿼리가 발생한다
   B. 데이터베이스의 속도가 빨라진다
   C. 트랜잭션 범위 밖에서 프록시 조회 시 예외가 발생할 수 있다
   D. 성능 저하의 주된 원인이 된다
   정답: C
   관련 키워드: Lazy Loading
   해설: 지연 로딩은 실제 객체가 필요할 때 DB를 조회하는데, 트랜잭션이 끝난 상태에서는 DB 커넥션이 없어 프록시 데이터를 가져올 수 없습니다.

3. Spring Data JPA에서 PageRequest를 사용하여 데이터를 조회할 때, 첫 번째 페이지의 인덱스는 무엇인가?
   A. 1
   B. 0
   C. null
   D. 첫 번째 데이터의 ID
   정답: B
   관련 키워드: Pageable
   해설: Spring Data JPA의 Pageable은 0부터 시작하는 페이지 인덱스를 사용합니다.

4. @OneToMany 단방향 매핑 시 흔히 발생하는 문제점은?
   A. 성능이 향상된다
   B. 매핑 테이블이 불필요하게 생성된다
   C. 데이터 수정 시 별도의 Update 쿼리가 추가로 발생할 수 있다
   D. 조인이 너무 빨라진다
   정답: C
   관련 키워드: OneToMany
   해설: 일대다 단방향은 연관 관계의 주인이 다른 테이블에 있으므로, 상태 변경 시 자신의 테이블이 아닌 연관 테이블에 Update 쿼리를 날려야 하는 구조적 비효율이 있습니다.

5. N+1 문제를 설명하는 가장 적절한 예시는?
   A. 데이터를 한 번에 조회하는 문제
   B. 조회 쿼리 1번 후 연관된 데이터 개수만큼 추가로 쿼리가 나가는 상황
   C. 페이징 시 전체 개수를 세는 쿼리
   D. DB 연결이 N개 생성되는 상황
   정답: B
   관련 키워드: Lazy Loading
   해설: N+1 문제는 부모 엔티티를 조회(1)한 후, 지연 로딩된 자식 엔티티를 순회(N)할 때 각각 추가 쿼리가 발생하는 현상을 의미합니다.

## 주차 과제

제목: 연관 관계와 페이징 실습

간단한 회원(User)과 게시글(Post) 엔티티를 생성하고, Pageable을 사용하여 게시글 목록을 페이징 처리하여 조회하는 API를 구현합니다.

[제출 체크리스트]
- User와 Post 엔티티에 @ManyToOne, @OneToMany 매핑
- Repository에서 Pageable을 파라미터로 받는 조회 메서드 작성
- Controller에서 0페이지, 사이즈 5로 요청하여 테스트
- 지연 로딩이 적용되었는지 쿼리 로그 확인

[필수 키워드] ManyToOne, Pageable, Lazy Loading, Repository

[수행 단계]
1. Entity 클래스에 @ManyToOne 및 @OneToMany 연관 관계 설정
2. JpaRepository 인터페이스에서 Page<Post> 반환형 메서드 선언
3. Controller에서 @GetMapping을 통해 Pageable 파라미터 수신 및 서비스 호출
