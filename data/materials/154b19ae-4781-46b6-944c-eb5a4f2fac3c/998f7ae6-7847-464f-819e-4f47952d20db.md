## 마크다운 학습 자료

### 📌 이번 주차 전체 지도
2주차에서 스프링 컨테이너와 의존성 주입(DI)을 통해 객체 간의 결합도를 낮추는 방법을 학습했습니다. 3주차인 이번 시간에는 클라이언트의 HTTP 요청을 직접적으로 처리하는 컨트롤러(Controller) 계층을 설계합니다. RESTful API의 철학을 바탕으로 @RestController를 활용해 요청과 응답을 다루는 법을 배웁니다. 학습 순서는 HTTP 메소드의 이해 → 컨트롤러 어노테이션 활용 → 데이터 전달 객체(DTO) 설계 → 응답 표준화 순으로 진행됩니다.

### 1️⃣ HTTP Methods (REST의 동사)
- **정의**: 서버 리소스에 수행할 작업을 정의하는 표준 인터페이스입니다.
- **원리**: GET(조회), POST(생성), PUT(전체 수정), PATCH(부분 수정), DELETE(삭제)로 구분됩니다.
- **예시**: 사용자를 생성할 때는 POST, 사용자 상세를 가져올 때는 GET을 사용합니다.
- **주의사항**: GET은 상태 변경이 없는 안전한(Safe) 연산이어야 합니다.
- **시험 포인트**: GET과 POST의 차이점(멱등성, 캐시 가능 여부).

### 2️⃣ @RestController의 역할
- **정의**: 스프링 MVC에서 웹 요청을 처리하는 컨트롤러 클래스에 붙이는 어노테이션입니다.
- **원리**: @Controller와 @ResponseBody가 합쳐진 형태로, 데이터(주로 JSON)를 직접 반환합니다.
- **예시**: `@RestController public class UserController { ... }`
- **주의사항**: 뷰 템플릿(HTML)을 반환할 때는 @Controller를 사용해야 합니다.
- **시험 포인트**: @RestController와 @Controller의 응답 값 차이.

### 3️⃣ RequestMapping과 경로 변수
- **정의**: 요청 URL과 메서드를 매핑하는 도구입니다.
- **원리**: @RequestMapping(또는 @GetMapping 등)으로 경로를 정의하고, @PathVariable로 동적 값을 가져옵니다.
- **예시**: `/users/{id}` 경로에서 `{id}`를 @PathVariable Long id로 바인딩합니다.
- **주의사항**: 경로 변수명과 매개변수명이 일치해야 오류가 없습니다.
- **시험 포인트**: @PathVariable과 @RequestParam의 용도 구분.

### 4️⃣ DTO (Data Transfer Object) 패턴
- **정의**: 계층 간 데이터 전달을 위한 순수 객체입니다.
- **원리**: 엔티티(Entity)를 외부로 노출하지 않고 필요한 필드만 포함하여 데이터를 캡슐화합니다.
- **예시**: `UserRequestDto`, `UserResponseDto` 클래스 생성.
- **주의사항**: 로직을 넣지 않고 데이터만 담는 필드와 Getter/Setter(또는 @Data)로 구성합니다.
- **시험 포인트**: 왜 엔티티를 직접 응답으로 보내면 안 되는가(보안, 순환 참조 문제).

### 5️⃣ 요청 데이터 바인딩 (@RequestBody)
- **정의**: JSON 형태의 요청 바디를 자바 객체로 변환합니다.
- **원리**: Jackson 라이브러리가 JSON 필드명과 DTO 필드명을 일치시켜 자동으로 값을 채워줍니다.
- **예시**: `@PostMapping public void create(@RequestBody UserRequestDto dto) { ... }`
- **주의사항**: JSON 필드명과 DTO의 변수명이 정확히 일치해야 합니다.
- **시험 포인트**: @RequestBody는 반드시 POST/PUT 등의 요청 본문이 있을 때 사용합니다.

### 6️⃣ ResponseEntity를 통한 응답 관리
- **정의**: HTTP 상태 코드, 헤더, 본문을 완벽하게 제어할 수 있는 응답 클래스입니다.
- **원리**: 개발자가 직접 상태 코드(200, 201, 404 등)를 명시하여 응답할 수 있습니다.
- **예시**: `return ResponseEntity.status(HttpStatus.CREATED).body(user);`
- **주의사항**: 모든 컨트롤러 메서드에서 ResponseEntity를 사용하면 코드 중복이 늘어날 수 있습니다.
- **시험 포인트**: 상태 코드 201(Created)의 의미.

### 📊 비교 정리표 1: HTTP 메소드 멱등성
| 메소드 | 역할 | 멱등성(Idempotency) | 안전성(Safe) |
| :--- | :--- | :--- | :--- |
| GET | 데이터 조회 | Yes | Yes |
| POST | 데이터 생성 | No | No |
| PUT | 데이터 전체 수정 | Yes | No |
| DELETE | 데이터 삭제 | Yes | No |

### 📊 비교 정리표 2: @PathVariable vs @RequestParam
| 구분 | 사용처 | URL 예시 |
| :--- | :--- | :--- |
| @PathVariable | 리소스 식별자(ID 등) | /users/1 |
| @RequestParam | 검색 필터, 쿼리 파라미터 | /users?name=kim |

### 🧪 실전 시나리오 3개
1. 게시글 생성: POST 요청을 받아 @RequestBody로 DTO를 받고, 성공 시 201 상태코드 반환.
2. 회원 검색: @PathVariable로 회원ID를 받아 DB에서 찾고, 없을 시 404 에러 반환.
3. 회원 정보 수정: PUT 요청으로 전체 정보를 받아 수정하고 200 OK와 수정본 반환.

### 🚨 자주 하는 실수 TOP 6
1. 엔티티를 컨트롤러 응답으로 그대로 반환(순환 참조 발생).
2. @RequestBody를 GET 요청에 사용하려 함(GET은 본문 없음).
3. DTO 필드명과 JSON 키 이름을 일치시키지 않음.
4. @PathVariable의 이름과 매개변수 이름을 다르게 설정.
5. 모든 오류에 200 OK만 반환하는 설계.
6. 무조건적인 @Data 사용으로 인한 Getter/Setter 오용.

### 💡 시험 포인트 & 암기 장치
- RESTful 핵심: URI는 자원(명사), 메소드는 동작(동사).
- DTO 사용 이유: 1. 보안(필드 숨기기), 2. 결합도 감소(엔티티 변경 시 API 영향 최소화).
- 상태 코드: 200(성공), 201(생성완료), 400(클라이언트 오류), 404(자원 없음), 500(서버 오류).

## 연습 퀴즈

1. RESTful API 설계 원칙 중 '멱등성(Idempotency)'에 대한 설명으로 옳은 것은?
   A. 한 번 요청하면 데이터가 항상 삭제된다.
   B. 여러 번 수행해도 결과가 동일하게 유지된다.
   C. 서버의 상태를 항상 변경하는 연산이다.
   D. 데이터 조회를 위한 유일한 방법이다.
   정답: B
   관련 키워드: HTTP Methods
   해설: 멱등성은 같은 요청을 여러 번 보내도 결과(리소스의 상태)가 처음과 동일하게 유지되는 성질을 의미합니다. PUT과 DELETE는 멱등하지만, POST는 호출할 때마다 새로운 자원이 생성되므로 멱등하지 않습니다.

2. @RestController의 주요 기능으로 옳은 것은?
   A. 템플릿 엔진을 통해 HTML 파일을 반환한다.
   B. @Controller와 @ResponseBody가 합쳐진 형태이다.
   C. 데이터베이스 연결을 직접 담당한다.
   D. 웹 요청을 처리하지 못하고 비즈니스 로직만 수행한다.
   정답: B
   관련 키워드: @RestController
   해설: @RestController는 컨트롤러 메서드가 반환하는 객체를 자동으로 JSON 등 데이터 형식으로 변환하여 HTTP 본문에 담아 보내는 기능을 수행합니다.

3. DTO(Data Transfer Object)를 사용하는 이유로 가장 부적절한 것은?
   A. 엔티티(Entity)를 외부로 노출하지 않아 보안을 유지한다.
   B. 엔티티 변경이 API 응답 구조에 미치는 영향을 최소화한다.
   C. 엔티티의 모든 비즈니스 로직을 컨트롤러에서 바로 쓰기 위해서다.
   D. API 요구사항에 맞는 데이터 형태만 전달할 수 있다.
   정답: C
   관련 키워드: DTO Pattern
   해설: DTO는 데이터를 전달하기 위한 단순 객체입니다. 비즈니스 로직은 도메인 계층(Entity/Service)에서 처리해야 하며, 컨트롤러에서 엔티티의 로직을 직접 수행하는 것은 계층 분리 원칙에 어긋납니다.

4. 리소스의 특정 식별자를 URL 경로에 포함할 때 사용하는 어노테이션은?
   A. @RequestParam
   B. @PathVariable
   C. @RequestBody
   D. @ModelAttribute
   정답: B
   관련 키워드: @RequestMapping
   해설: @PathVariable은 '/users/{id}'와 같이 경로의 일부를 변수로 바인딩할 때 사용합니다.

5. HTTP 상태 코드 201(Created)을 사용하는 상황으로 가장 적절한 것은?
   A. 정상적으로 데이터를 조회했을 때
   B. 클라이언트의 요청이 잘못되었을 때
   C. 리소스 생성 요청이 성공하여 새로운 자원이 만들어졌을 때
   D. 서버 내부에서 에러가 발생했을 때
   정답: C
   관련 키워드: ResponseEntity
   해설: 201 Created는 POST 등의 요청을 통해 서버 내부에 리소스가 성공적으로 생성되었음을 알리는 표준 코드입니다.
