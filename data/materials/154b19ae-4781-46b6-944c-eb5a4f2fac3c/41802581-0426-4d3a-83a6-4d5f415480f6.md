# 6주차 학습 자료 — 데이터 검증과 보안 — 데이터 유효성 검사

## 학습 자료

## 마크다운 학습 자료 — 스프링부트 데이터 검증과 보안

### 📌 이번 주차 전체 지도
5주차에서 배운 글로벌 예외 처리(Global Exception Handling) 체계 위에서, 이제는 입력되는 데이터의 신뢰성을 확보하는 '데이터 유효성 검사(Validation)'에 집중합니다. 클라이언트의 요청은 언제나 위협적이라는 보안의 제1원칙을 바탕으로, Bean Validation을 통한 DTO 검증 체계를 구축하고, 실패 시 적절한 피드백을 주는 표준 프로세스를 학습합니다.

### 1️⃣ Bean Validation (JSR-380)
- 정의: 자바 객체의 제약 조건을 정의하고 검증하기 위한 표준 규격.
- 원리: 애노테이션(Annotation)을 필드에 선언하여 선언적으로 검증 로직을 구현.
- 예시: `@NotNull`, `@Min(1)`, `@Email` 등을 DTO 필드에 사용.
- 주의사항: DTO 클래스에만 적용하며, 엔티티(Entity) 레벨 검증은 지양.
- 시험 포인트: Hibernate Validator가 스프링 부트의 기본 구현체라는 점.

### 2️⃣ @Valid 와 @Validated
- 정의: 컨트롤러 메서드 인자에 검증 수행을 지시하는 애노테이션.
- 원리: 스프링 MVC가 인자를 바인딩할 때 검증기를 호출.
- 예시: `@PostMapping("/save") public void save(@Valid @RequestBody UserDTO dto)`.
- 주의사항: 반드시 BindingResult와 짝을 이루어 사용해야 오류가 발생해도 서버가 죽지 않음.
- 시험 포인트: @Validated는 그룹화 검증을 지원함.

### 3️⃣ BindingResult의 활용
- 정의: 유효성 검사 결과를 담는 객체.
- 원리: @Valid 바로 뒤에 위치시켜야 하며, 검사 실패 시 에러 내용을 내부적으로 보관.
- 예시: `if(bindingResult.hasErrors()) { return errorResponse; }`.
- 주의사항: 에러를 처리하지 않고 방치하면 400 Bad Request가 기본으로 발생.
- 시험 포인트: BindingResult 파라미터 위치는 반드시 검증 객체 바로 뒤!

### 4️⃣ 클라이언트 무결성과 보안
- 정의: 데이터가 변경되지 않고 규칙을 지켰는지 확인.
- 원리: Sanitization(데이터 정화)과 Validation을 통해 비정상적인 입력 차단.
- 예시: XSS 방지를 위한 `<script>` 태그 입력 제한.
- 주의사항: 서버측 검증은 필수이며, 클라이언트측 검증은 사용자 편의를 위한 보조 수단.
- 시험 포인트: 클라이언트는 항상 해커의 공격 통로가 될 수 있음을 인지.

### 5️⃣ 커스텀 검증 어노테이션
- 정의: 표준 어노테이션으로 해결할 수 없는 복합적인 로직 구현.
- 원리: ConstraintValidator 인터페이스를 구현하여 로직 작성.
- 예시: 패스워드에 특수문자 포함 여부 검증.
- 주의사항: 재사용성을 고려하여 범용적으로 설계.
- 시험 포인트: @Constraint 애노테이션 내에 validator 클래스 지정.

### 6️⃣ 에러 응답 표준화
- 정의: 유효성 검사 실패 시 일관된 에러 JSON 반환.
- 원리: ErrorCode와 메시지를 담은 공통 응답 DTO 설계.
- 예시: `{ "status": 400, "message": "입력값이 올바르지 않습니다.", "errors": [...] }`.
- 주의사항: 상세한 에러 로그를 클라이언트에게 그대로 노출하지 않도록 주의.
- 시험 포인트: 사용자 친화적이면서도 보안상 안전한 메시지 제공.

### 📊 비교 정리표 1: @Valid vs @Validated
| 구분 | @Valid | @Validated |
| :--- | :--- | :--- |
| 제공 주체 | 자바 표준(JSR-380) | 스프링 프레임워크 |
| 그룹 검증 | 미지원 | 지원 |
| 용도 | 컨트롤러 계층 검증 | 서비스/컨트롤러 계층 겸용 |

### 📊 비교 정리표 2: 유효성 검사 시점
| 위치 | 장점 | 단점 |
| :--- | :--- | :--- |
| 프론트엔드 | 즉각적 피드백, 부하 감소 | 우회 가능, 보안상 취약 |
| 백엔드 | 신뢰성 확보, 최종 방어선 | 서버 리소스 소모 |

### 🧪 실전 시나리오 3개
1. 회원가입: DTO에 @Email, @Size(min=8)을 적용하여 필수 항목 검증 및 BindingResult로 처리.
2. 상품 수정: @Min(0)을 적용해 가격이 음수가 되는 것을 방지.
3. 게시글 댓글: 악성 스크립트 삽입 방지를 위한 정화(Sanitization) 규칙 적용.

### 🚨 자주 하는 실수 TOP 6
1. BindingResult를 @Valid 객체 뒤에 선언하지 않음.
2. 엔티티 클래스에 검증 어노테이션을 마구잡이로 사용.
3. 검증 실패 시 처리 로직을 구현하지 않아 400 에러를 그대로 노출.
4. @Size 어노테이션을 숫자 범위 검증에 사용(문자열용).
5. 프론트엔드 검증만 믿고 백엔드에서 검증을 생략.
6. 에러 메시지를 하드코딩하여 다국어 지원이 어려움.

## 연습 퀴즈

1. 스프링 부트에서 @Valid 어노테이션을 사용하여 유효성 검사를 수행할 때, 검증 결과가 담기는 객체는 무엇인가?
   A. BindingResult
   B. Validator
   C. ConstraintViolation
   D. ValidationResult
   정답: A
   관련 키워드: BindingResult
   해설: BindingResult는 @Valid 어노테이션 바로 뒤에 위치하여, 유효성 검사 실패 시 발생한 에러 정보들을 담는 객체입니다.

2. 데이터 유효성 검사를 수행할 때 엔티티(Entity)가 아닌 DTO(Data Transfer Object)를 사용하는 주된 이유는?
   A. 성능 향상
   B. 데이터베이스 부하 감소
   C. 계층 간의 결합도를 낮추고 데이터 보호
   D. 검증 로직의 단순화
   정답: C
   관련 키워드: RequestDTO
   해설: 엔티티를 직접 외부에 노출하면 DB 구조가 드러나고 의도치 않은 데이터 수정이 발생할 수 있으므로, DTO를 사용하여 필요한 데이터만 검증하고 전달합니다.

3. 클라이언트의 요청을 신뢰하지 말아야 하는 가장 큰 이유는?
   A. 클라이언트는 서버보다 느리기 때문
   B. 네트워크 통신 중 에러가 발생할 수 있기 때문
   C. 의도적으로 조작된 데이터를 보낼 수 있는 공격 통로이기 때문
   D. 데이터 포맷이 달라질 수 있기 때문
   정답: C
   관련 키워드: Security Basic
   해설: 보안의 기초는 모든 입력값은 오염될 수 있다는 전제에서 시작하며, 따라서 서버측에서의 엄격한 검증이 필수적입니다.

4. @Validated와 @Valid의 차이점으로 옳은 것은?
   A. @Validated는 자바 표준이다
   B. @Validated는 검증 그룹 기능을 지원한다
   C. @Valid가 스프링 전용 기능이다
   D. 둘은 기능적으로 완전히 동일하다
   정답: B
   관련 키워드: Validation
   해설: @Validated는 스프링에서 제공하는 어노테이션으로, 유효성 검사 그룹을 지정할 수 있는 기능을 추가로 제공합니다.

5. Bean Validation 어노테이션 중 문자열의 길이를 제한할 때 사용하는 것은?
   A. @NotNull
   B. @Max
   C. @Size
   D. @Email
   정답: C
   관련 키워드: Bean Validation
   해설: @Size는 컬렉션, 배열, 문자열의 길이를 제한할 때 사용하는 표준 어노테이션입니다.
