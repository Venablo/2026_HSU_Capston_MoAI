# 5주차 학습 자료 — 비즈니스 로직과 예외 처리 — 서비스 계층 구축

## 학습 자료

## 마크다운 학습 자료

### 📌 이번 주차 전체 지도
지난 4주차에서 학습한 데이터 접근 계층(Repository Layer)이 DB와의 직접적인 소통을 담당했다면, 이번 5주차에는 애플리케이션의 두뇌인 서비스 계층(Service Layer)을 구축합니다. 우리는 비즈니스 로직을 컨트롤러에서 분리하여 서비스 계층으로 이동시키고, 이 과정에서 발생 가능한 다양한 예외(Exception) 상황을 우아하게 처리하는 방법을 배웁니다. 서비스 계층 설계부터 전역 예외 처리기(@ControllerAdvice) 구현까지, 실무형 애플리케이션 구조를 완성하는 것이 이번 주 학습의 핵심 순서입니다.

### 1️⃣~6️⃣ 핵심 개념 6개 상세

1. 서비스 계층(Service Layer)의 역할: 컨트롤러와 데이터 접근 계층 사이에서 비즈니스 규칙을 수행하는 중간 다리입니다. 정의: 컨트롤러는 요청 수신 및 응답 반환만, 데이터 계층은 DB 작업만 수행하도록 분리합니다. 원리: DI(의존성 주입)를 통해 서비스를 주입받아 사용합니다. 예시: 회원가입 시 중복 검사 후 저장 로직. 주의사항: 서비스에 너무 많은 책임이 몰리지 않도록 설계해야 합니다. 시험 포인트: 왜 컨트롤러에 로직을 넣지 않는가? (재사용성 및 유지보수).

2. 트랜잭션(@Transactional): 데이터베이스의 논리적인 작업 단위입니다. 원리: 여러 작업을 하나로 묶어 '모두 성공'하거나 '모두 실패'하게 만듭니다. 예시: 결제 시 계좌 차감과 포인트 적립이 동시에 일어나야 함. 주의사항: 메서드 단위로 적용하며, 예외 발생 시 자동으로 롤백(Rollback) 됩니다. 시험 포인트: @Transactional이 적용된 메서드 내에서 발생한 에러 처리.

3. 전역 예외 처리기(@ControllerAdvice): 애플리케이션 전역에서 발생하는 예외를 한곳에서 관리합니다. 원리: @ExceptionHandler를 사용하여 특정 예외마다 별도의 응답을 정의합니다. 예시: 404 Not Found, 500 Internal Server Error를 일관된 형식으로 반환. 주의사항: 너무 광범위한 예외(Exception.class)는 신중하게 사용해야 합니다. 시험 포인트: @RestControllerAdvice와의 차이점.

4. 커스텀 예외(Custom Exception): 비즈니스 상황에 맞는 명확한 오류를 정의합니다. 원리: RuntimeException을 상속받아 고유한 에러 코드와 메시지를 가집니다. 예시: UserNotFoundException. 주의사항: 예외는 프로그램의 흐름 제어용이 아닌 '비정상 상태'를 알리기 위해 사용해야 합니다. 시험 포인트: 커스텀 예외를 사용할 때의 장점(가독성).

5. 비즈니스 로직(Business Logic)의 캡슐화: 로직을 객체 지향적으로 처리하는 과정입니다. 원리: 데이터(Domain)와 로직(Method)을 함께 응집시킵니다. 예시: User 객체 내에 비밀번호 변경 메서드를 구현. 주의사항: Setter 남발을 방지하고 의미 있는 메서드를 작성하세요. 시험 포인트: 비즈니스 로직의 올바른 배치 위치.

6. 유효성 검사(Validation): 요청 데이터가 유효한지 확인합니다. 원리: @Valid와 @NotNull 등 애노테이션을 활용하여 서비스 실행 전 검증합니다. 예시: 회원가입 시 이메일 형식 확인. 주의사항: 계층 간 경계에서 검증하여 불필요한 DB 접근을 차단해야 합니다. 시험 포인트: @Valid 작동 원리.

### 📊 비교 정리표 2개

| 비교 항목 | 컨트롤러(Controller) | 서비스(Service) |
|---|---|---|
| 주요 역할 | 요청 수신/응답 반환 | 비즈니스 로직 수행 |
| 로직 작성 여부 | 지양(비추천) | 필수(권장) |
| 재사용성 | 낮음 | 매우 높음 |
| 의존성 | HTTP 인터페이스에 의존 | 도메인 로직에 의존 |

| 비교 항목 | checked Exception | unchecked(Runtime) Exception |
|---|---|---|
| 트랜잭션 롤백 | 자동 롤백 안 됨 | 자동 롤백 됨 |
| 컴파일 확인 | 컴파일 타임에 강제 확인 | 런타임에 확인 |
| 스프링 권장 | 사용 지양 | 적극 사용 권장 |

### 🧪 실전 시나리오 3개
1. 회원가입 실패 시: 중복된 이메일이 입력되면 'DuplicatedEmailException'을 던지고, 전역 처리기에서 409 Conflict 응답을 보냄.
2. 잔액 부족 결제: 포인트가 부족하면 'InsufficientPointsException'을 발생시켜 결제 트랜잭션을 롤백하고 사용자에게 알림.
3. 상품 조회 시: 존재하지 않는 상품 ID 호출 시 'ProductNotFoundException' 발생, 404 에러로 매핑.

### 🚨 자주 하는 실수 TOP 6
1. 서비스 계층에서 HTTP 상태 코드(HttpStatus)를 직접 반환함(분리 원칙 위배).
2. 모든 예외를 try-catch로 잡아버려 예외가 어디서 났는지 모르게 함.
3. @Transactional을 잊어 데이터 불일치 발생.
4. 커스텀 예외를 만들지 않고 런타임 에러만 던짐.
5. 유효성 검사(@Valid)를 컨트롤러에서 하지 않고 서비스에서 복잡하게 구현함.
6. 예외 메시지에 민감한 정보(DB 구조 등)를 그대로 노출함.

### 💡 시험 포인트 & 암기 장치
- 컨트롤러는 '입구', 서비스는 '두뇌'.
- @Transactional은 성공하면 커밋, 실패하면 롤백(만능 도우미).
- @ControllerAdvice는 예외를 모아 처리하는 '종합 상황실'.
- 암기법: "서비스 계층은 로직만 담당하고, 응답의 형태는 컨트롤러가 담당한다!"

## 연습 퀴즈

1. 서비스 계층(Service Layer)을 사용하는 주된 이유로 가장 적절하지 않은 것은?
   A. 비즈니스 로직의 재사용성을 높이기 위해
   B. HTTP 요청/응답 처리를 자동화하기 위해
   C. 유지보수성을 향상시키기 위해
   D. 로직을 분리하여 컨트롤러의 부담을 줄이기 위해
   정답: B
   관련 키워드: Service Layer
   해설: HTTP 요청/응답 처리는 컨트롤러의 역할입니다. 서비스 계층은 오직 비즈니스 로직에만 집중해야 합니다.

2. @Transactional 애노테이션에 대한 설명으로 옳은 것은?
   A. 기본적으로 모든 예외에 대해 롤백한다.
   B. 체크드 예외(Checked Exception) 발생 시에도 항상 롤백된다.
   C. 여러 DB 작업을 하나의 논리적 단위로 묶어준다.
   D. 데이터 조회 전용 메서드에만 사용해야 한다.
   정답: C
   관련 키워드: @Transactional
   해설: @Transactional은 논리적인 트랜잭션을 보장하며, 기본적으로 RuntimeException에 대해서만 자동으로 롤백을 수행합니다.

3. 전역 예외 처리를 위해 사용하는 스프링의 어노테이션은 무엇인가?
   A. @RestController
   B. @Service
   C. @ControllerAdvice
   D. @Transactional
   정답: C
   관련 키워드: @ControllerAdvice
   해설: @ControllerAdvice는 애플리케이션 전역에서 발생하는 예외를 인터셉트하여 일관된 처리를 할 수 있게 돕습니다.

4. 컨트롤러에 비즈니스 로직을 작성하지 말아야 하는 이유로 가장 타당한 것은?
   A. 컨트롤러는 메모리를 많이 차지하기 때문에
   B. 다른 계층에서 해당 로직을 재사용할 수 없게 되기 때문에
   C. 컨트롤러에서는 데이터 접근이 불가능하기 때문에
   D. 스프링이 컨트롤러 내의 로직 실행을 차단하기 때문에
   정답: B
   관련 키워드: Business Logic
   해설: 로직이 컨트롤러에 있으면 다른 API나 배치 작업 등에서 해당 로직을 재사용할 수 없고 유지보수가 어렵습니다.

5. 커스텀 예외를 구현할 때 주로 상속받는 클래스는?
   A. Error
   B. Exception (Checked)
   C. RuntimeException
   D. Throwable
   정답: C
   관련 키워드: Exception Handling
   해설: 스프링 환경에서는 트랜잭션 롤백과 처리의 유연성을 위해 Checked Exception보다는 RuntimeException을 상속받는 것을 권장합니다.

## 주차 과제

제목: 비즈니스 로직 분리 및 전역 예외 처리기 구현

기존 컨트롤러에 작성된 간단한 '사용자 정보 저장' 로직을 서비스 계층으로 분리하고, 존재하지 않는 ID 조회 시 404 에러를 반환하는 전역 예외 처리기를 구현하세요.

[제출 체크리스트]
- UserController에서 비즈니스 로직을 제거하고 UserService 클래스 호출
- UserService 내에 @Transactional 적용
- EntityNotFoundException 커스텀 예외 생성
- @RestControllerAdvice 클래스 구현 및 404 상태코드 매핑

[필수 키워드] Service, Transactional, RestControllerAdvice, RuntimeException

[수행 단계]
1. 1. UserController 리팩토링 및 서비스 의존성 주입
2. 2. 서비스 클래스 생성 및 비즈니스 로직 이전
3. 3. GlobalExceptionHandler 클래스 생성 및 예외 처리 로직 추가
