# 2주차 약점 보충 자료

## 약점 보충 학습

### 🔁 약점 보충 학습 목표
학습자님께서 파이널 퀴즈에서 오답을 기록한 '스프링 부트(Spring Boot) 핵심 메커니즘'들은 현대 자바 웹 개발의 효율성을 극대화하는 근간입니다. 이번 학습의 목표는 단순히 라이브러리를 가져다 쓰는 수준을 넘어, '왜 스프링 부트가 복잡한 설정 없이 애플리케이션을 즉시 구동할 수 있는지'에 대한 원리를 이해하는 데 있습니다. 의존성 관리(Dependency Management)부터 자동 설정(Auto Configuration)까지의 흐름을 파악함으로써, 설정의 마법을 걷어내고 프레임워크의 동작 방식을 명확히 체득하여 실무형 개발 역량을 강화하고자 합니다.

### 키워드별 심화 정리

#### 1. 스프링 부트 스타터 (Spring Boot Starter)
**정의:** 특정 목적을 달성하기 위해 필요한 라이브러리들의 묶음(Dependency Descriptor)입니다.
**원리:** 개발자가 일일이 필요한 의존성을 나열할 필요 없이, 'spring-boot-starter-web'과 같이 하나의 의존성만 추가하면 내부적으로 필요한 웹 서버, Jackson, Logging, Validation 등 연관 라이브러리가 자동으로 관리되는 '의존성 집합체'입니다. 이는 BOM(Bill of Materials) 방식을 통해 버전 호환성이 검증된 라이브러리들만 가져오도록 설계되어 있습니다.
**예시:** API 서버를 만들 때 `spring-boot-starter-web` 하나만 추가하면, 내장 톰캣(Embedded Tomcat)과 Spring MVC 라이브러리가 자동으로 포함됩니다.
**자주 하는 실수:** 여러 스타터를 중복으로 추가하여 라이브러리 버전 충돌을 일으키거나, 필요한 최소한의 스타터 대신 너무 많은 라이브러리를 한꺼번에 포함해 애플리케이션의 크기(Fat JAR)를 불필요하게 키우는 경우가 많습니다.

#### 2. 의존성 관리 (Dependency Management)
**정의:** 프로젝트 내에서 사용하는 라이브러리들의 버전 간 충돌을 방지하고 호환성을 유지하는 시스템입니다.
**원리:** 스프링 부트는 `spring-boot-dependencies`라는 부모 POM을 통해 관리되는 수많은 라이브러리의 버전을 미리 정의해둡니다. 덕분에 사용자는 특정 라이브러리의 버전을 명시하지 않아도 부모 설정에 지정된 가장 안정적인(Compatible) 버전을 자동으로 상속받게 됩니다.
**예시:** `spring-boot-starter-parent`를 상속받으면, Spring Framework 버전이나 Hibernate 등의 버전 선언 없이도 항상 호환되는 버전이 주입됩니다.
**자주 하는 실수:** `dependency-management`의 역할을 무시하고 임의로 모든 라이브러리에 버전을 강제로 고정하여, 오히려 스프링 부트가 보장하는 버전 최적화 기능을 상실하게 만드는 실수입니다.

#### 3. 내장 톰캣 (Embedded Tomcat)
**정의:** 애플리케이션 안에 서블릿 컨테이너(Servlet Container)가 내장되어 별도의 외부 WAS 설치 없이 실행 가능한 형태입니다.
**원리:** 과거에는 WAR 파일을 외장 서버(Tomcat 등)에 배포해야 했으나, 스프링 부트는 `main` 메소드 실행 시 내장된 톰캣 엔진을 호출하여 웹 서버를 구동합니다. 이 덕분에 JAR 파일 하나만으로 서비스 배포가 가능한 'Self-contained' 구조를 갖습니다.
**예시:** `public static void main` 메소드를 실행하면 콘솔에 'Tomcat initialized with port(s): 8080' 메시지가 뜨며 웹 서버가 즉시 구동됩니다.
**자주 하는 실수:** 개발용으로 내장 톰캣을 사용하는 것을 간과하고, 운영 환경에서도 무조건 외장 WAS를 고집하며 복잡한 서버 설정을 추가하려고 하는 것입니다. 부트의 철학은 실행 가능한 아카이브(Executable JAR)입니다.

#### 4. 자동 설정 (Auto Configuration)
**정의:** 클래스패스(Classpath)에 있는 라이브러리들과 환경 설정을 바탕으로 스프링 빈(Bean)을 자동으로 등록해주는 기능입니다.
**원리:** `@EnableAutoConfiguration` 어노테이션이 핵심이며, 스프링 부트가 시작될 때 '이 라이브러리가 클래스패스에 있나?', '이 빈이 이미 등록되어 있나?'를 조건부(Conditional)로 검사하여 빈을 자동으로 생성합니다. `spring.factories` 파일 내부에 정의된 설정 클래스들이 이 마법을 수행합니다.
**예시:** H2 데이터베이스 드라이버를 의존성에 추가하면, 별도의 `DataSource` 빈 설정 없이도 부트가 자동으로 메모리 DB용 설정을 생성합니다.
**자주 하는 실수:** 자동 설정이 무엇을 하는지 모른 채 본인이 직접 수동 설정을 중복으로 작성하여, 자동 설정된 빈과 충돌을 일으키는 경우입니다.

#### 5. 애플리케이션 프로퍼티 (Application.properties)
**정의:** 애플리케이션의 실행 환경 설정 및 외부 설정을 담당하는 키-값(Key-Value) 형태의 설정 파일입니다.
**원리:** `application.properties` 혹은 `application.yml`은 프로젝트의 설정을 중앙 집중화합니다. 스프링 부트는 우선순위(Priority)에 따라 환경 변수, 커맨드 라인 인자, 설정 파일 순으로 값을 로드하며, `application.properties`의 설정 값은 `@Value`나 `@ConfigurationProperties`를 통해 자바 객체로 바인딩됩니다.
**예시:** `server.port=9090`을 작성하면, 내장 톰캣이 기본 8080이 아닌 9090 포트로 동작하게 됩니다.
**자주 하는 실수:** 복잡한 설정을 모두 프로퍼티 파일에만 의존하거나, 환경별(dev/prod) 설정을 분리하지 않고 하나의 파일에 몰아넣어 운영상의 혼란을 초래하는 것입니다.

### 비교 정리표

| 구분 | 스프링 부트 스타터 | 자동 설정 (Auto Config) | 의존성 관리 | 내장 톰캣 | 애플리케이션 프로퍼티 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **핵심 역할** | 라이브러리 묶음 제공 | 빈 자동 생성 및 등록 | 버전 호환성 최적화 | 웹 서버 내장 | 환경 변수 설정 |
| **작동 시점** | 빌드 타임 | 런타임(시작 시) | 빌드 타임 | 런타임(구동 시) | 런타임(주입 시) |
| **필수 여부** | 선택 (권장) | 자동 수행 | 자동 수행 | 선택 가능 | 필수 (대체 가능) |

### 핵심 암기 포인트 & 체크리스트

- [ ] **Starter:** '어떤 기능을 추가하려면 어떤 스타터를 써야 하지?'를 생각하자. (예: DB는 `spring-boot-starter-data-jpa`)
- [ ] **Dependency Management:** 버전을 명시하지 않는 것이 부트의 정석이다. `parent` POM의 힘을 믿자.
- [ ] **Embedded Tomcat:** WAS 설치가 아니라 `main` 실행이 서버 실행이다. JAR 배포를 기억하자.
- [ ] **Auto Configuration:** `@Conditional` 조건이 핵심이다. 클래스패스에 라이브러리가 있는지 확인하자.
- [ ] **Application.properties:** 설정 우선순위를 기억하자. (환경 변수 > properties)

**암기 팁:** 스프링 부트는 '설정(Configuration)을 제거하고, 관례(Convention)에 따라 자동으로(Auto) 동작하게 한다'는 철학을 가집니다. 문제가 발생하면 자동 설정 보고서(`--debug` 옵션 사용)를 확인하세요!
